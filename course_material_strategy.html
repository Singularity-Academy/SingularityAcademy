Course Material Storage Strategy

Storing diverse course materials (PDFs, videos, audio, text files, inline text) requires a flexible and scalable approach. Here's a breakdown of how to manage the metadata and the actual content.

1. Storing Material Metadata (in the Database)

Regardless of where the actual material content resides, metadata about each material will always be stored in our database. This allows the application to organize, find, and display materials.

Proposed CourseMaterial Database Model

This model is designed to handle various material types, storing metadata in the database and linking to externally stored files or inline content.

# In ai_engine/db.py (using Tortoise-ORM)

class CourseMaterial(models.Model):
    id = fields.BigIntField(pk=True)
    course = fields.ForeignKeyField('models.Course', related_name='materials')
    title = fields.CharField(max_length=255, null=False)
    description = fields.TextField(null=True, blank=True)
    
    material_type = fields.CharField(max_length=50, null=False, 
                                     description="E.g., PDF, VIDEO, INLINE_TEXT, EXTERNAL_LINK")
    
    # For INLINE_TEXT type material
    content_text = fields.TextField(null=True, blank=True) 
    
    # For file-based materials or external links
    # If local FS: relative path from MEDIA_ROOT
    # If cloud storage (S3): object key/path in bucket
    # If EXTERNAL_LINK: full URL
    file_path_or_url = fields.TextField(null=True, blank=True) 
    
    original_filename = fields.CharField(max_length=255, null=True, blank=True)
    mime_type = fields.CharField(max_length=100, null=True, blank=True)
    file_size = fields.BigIntField(null=True, description="File size in bytes")

    uploaded_by = fields.ForeignKeyField('models.User', related_name='uploaded_materials', null=True)
    display_order = fields.IntField(default=0)

    created_at = fields.DatetimeField(auto_now_add=True)
    updated_at = fields.DatetimeField(auto_now=True)

    class Meta:
        table = "course_materials"
        ordering = ["course_id", "display_order"]

Key Metadata Fields:

  • material_type: Crucial! Determines how to handle the material (e.g., display content_text or fetch from file_path_or_url).
  • content_text: Stores actual text for INLINE_TEXT type materials.
  • file_path_or_url: Stores the path/key for files (local or cloud) or the URL for external links.
  • original_filename, mime_type, file_size: Essential metadata for uploaded files.

2. Storing Actual Material Content

This section discusses where the file data (PDFs, MP4s, etc.) or larger text content should live.

Storage Option Description Pros Cons Verdict
A. Directly in Database (BLOBs/TEXT) Storing file content within database columns. Data and metadata co-located (for small text). Major performance hit for binaries.
Database bloat & large backups.
Inefficient for serving/streaming media.
No CDN benefits. 		Strongly discouraged for binary files. OK for small, inline text.
B. Server's File System Storing files on the same server as the application. Simple for small-scale.
Fast local access. 		Scalability issues (needs shared FS for multi-instance).
Separate backup management.
Deployment path complexities. 		Viable for very small apps or local dev. Problematic at scale.
C. Cloud Object Storage (e.g., AWS S3, Google Cloud Storage) Using dedicated cloud services for file storage. Highly Scalable & Durable.
Cost-effective for large files.
Efficient serving (direct or via CDN).
Advanced features (versioning, security).
Decouples storage. 		Slightly more complex initial setup.
Potential bandwidth costs (data egress). 		Most Recommended for production. Best balance of scalability, reliability, performance, and cost for files.

3. Recommended Hybrid Strategy

This strategy combines the strengths of database metadata storage with flexible content storage.

Strategy Details:

  1. For Files (PDF, MP4, MP3, downloadable TXT, images):
    • Store actual file content in: Cloud Object Storage (e.g., AWS S3).
    • In the CourseMaterial database record:
      • Set material_type (e.g., "VIDEO").
      • Store the S3 object key (path within bucket) in file_path_or_url.
      • Populate original_filename, mime_type, file_size.
      • content_text would be NULL.
  2. For Plain Text (inline notes, instructions, code snippets):
    • Store actual text content in: The database.
    • In the CourseMaterial database record:
      • Set material_type to "INLINE_TEXT".
      • Store the text content in the content_text field.
      • file_path_or_url and file-specific metadata fields would be NULL.
  3. For External Links (linking to external articles, videos, etc.):
    • Store URL in: The database.
    • In the CourseMaterial database record:
      • Set material_type to "EXTERNAL_LINK".
      • Store the full external URL in file_path_or_url.
      • content_text and file-specific metadata fields would be NULL.

Implementation Considerations

  • File Upload Endpoint: Your Sanic application will need an endpoint to:
    1. Receive uploaded files.
    2. Transfer them to the chosen storage (e.g., S3).
    3. Create a CourseMaterial metadata record in the database.
  • Serving/Accessing Files:
    • For cloud storage (S3): Generate secure, time-limited pre-signed URLs from your backend. The client uses these URLs to fetch files directly from S3. This is secure and efficient.
    • For local files: Sanic can serve them, but a dedicated web server like Nginx is better for production.
  • Security:
    • Securely manage cloud credentials (environment variables, secrets managers).
    • Implement proper access control for who can upload and access materials.
  • Libraries:
    • For AWS S3: boto3 (Python SDK).
    • For file uploads in Sanic: request.files.

This comprehensive approach ensures your system is flexible, scalable, and efficient for managing diverse course materials.
