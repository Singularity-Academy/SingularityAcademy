Endpoint: /principal-ai/ws/chat

Protocol: WebSocket (ws:// or wss://)

Framework: Sanic WebSocket with async/await pattern

Overview: This document describes the complete lifecycle of a WebSocket connection to the Principal AI chat system, including authentication, message processing, streaming responses, tool execution, and connection termination.

Phase 1: Connection Establishment

Initial WebSocket Connection

When a client connects to the WebSocket endpoint, the following occurs:

  • Server generates a unique 8-character session ID
  • Client IP address is logged for security tracking
  • LLM (Language Learning Model) instance is initialized
  • Connection enters authentication waiting state
client_ip = request.remote_addr or request.ip session_id = str(uuid.uuid4())[:8] logger.info(f"New WebSocket connection from {client_ip} (session: {session_id})") llm = LLM()

Phase 2: Authentication

Token-Based Authentication Process

2.1 Authentication Message Required

The server immediately waits for an authentication message from the client:

{ "token": "your_jwt_token_here" }

2.2 Token Validation Steps

  1. Message Format Validation: Must be valid JSON with "token" field
  2. Token Decoding: JWT token is decoded and validated
  3. Claims Extraction: User ID is extracted from token claims
  4. Database Verification: User existence is verified in database

2.3 Authentication Success Response

On successful authentication, server sends:
{ "type": "auth_success", "message": "Authentication successful", "user_id": "user_uuid_here" }

2.4 Authentication Error Responses

Common authentication failures:
Error Code Condition WebSocket Close Code
INVALID_AUTH_FORMAT Missing token field or invalid JSON 1008
INVALID_TOKEN Token decode failure or expired 1008
INVALID_TOKEN_CLAIMS Missing user ID in token claims 1008
USER_NOT_FOUND User ID not found in database 1008

Phase 3: Session Initialization

Chat Instance and Tool Setup

3.1 Chat History Initialization

  • Retrieve or create PrincipalChat instance for the user
  • Load existing chat history (last 10 messages)
  • Initialize with system prompt if no history exists

3.2 AI Tools Configuration

Five course management tools are configured for the session:

tools = [ CreateCourseTool(user_id=user.id), GetCourseTool(user_id=user.id), ListCoursesTool(user_id=user.id), UpdateCourseTool(user_id=user.id), DeleteCourseTool(user_id=user.id), ]

3.3 Chat History Transmission

Server sends recent chat history to client:

{ "type": "history_messages", "messages": [ { "role": "user", "content": "Previous message content", "timestamp": "2024-01-15T10:30:00.000Z", "courses": [] }, { "role": "assistant", "content": "Previous AI response", "timestamp": "2024-01-15T10:30:15.000Z", "courses": [] } ] }

Phase 4: Message Processing Loop

Continuous Message Handling

Once initialized, the connection enters an infinite loop processing incoming messages. The server supports three message types:

4.1 Chat Messages ("message" type)

Client → {"type": "message", "content": "user question"} → Server

Message Processing Pipeline:

  1. Save User Message: Add to chat history with timestamp
  2. Initialize Streaming: Create WebSocket streaming callback
  3. LLM Processing: Generate response using pre-configured tools
  4. Stream Response: Send tokens in real-time to client
  5. Save AI Response: Store complete response in chat history

Streaming Response Format:

Response Start:
{ "type": "response_start", "message_id": "unique_message_id", "timestamp": "2024-01-15T10:30:00.000Z" }
Token Stream: Raw text content (no JSON wrapper)
"This is a streaming response token by token..."
Tool Execution (if triggered):
{ "type": "tool_call_start", "tool_call": { "name": "CreateCourseTool", "status": "running", "parameters": {"input": "course creation request"} }, "timestamp": "2024-01-15T10:30:05.000Z" }
Response End:
{ "type": "response_end", "message_id": "unique_message_id", "timestamp": "2024-01-15T10:30:15.000Z" }

4.2 Chat Reset ("message-reset" type)

Client → {"type": "message-reset"} → Server

Clears all chat history except the system prompt and responds with:

{ "type": "message-reset-success", "message": "Chat history reset" }

4.3 Course Operations ("course" type)

Client → {"type": "course", "content": "course request"} → Server

Handles specialized course management requests through dedicated tool execution.

Tool Execution Lifecycle

AI Tool Integration and Execution

Available Tools

Tool Name Purpose User Scoped
CreateCourseTool Create new courses Yes
GetCourseTool Retrieve specific course data Yes
ListCoursesTool List user's courses Yes
UpdateCourseTool Modify existing courses Yes
DeleteCourseTool Remove courses Yes

Tool Execution Flow

  1. Tool Trigger: LLM determines tool usage based on user input
  2. Tool Start Signal: Client receives tool execution notification
  3. Tool Processing: Server executes tool with user-scoped permissions
  4. Tool Completion: Results are streamed back to client
  5. Course Updates: Relevant course data changes are broadcasted

Error Handling and Recovery

Connection-Level Errors

  • WebsocketClosed: Client disconnection during operation
  • RuntimeError: Unexpected connection termination
  • JSON Decode Errors: Invalid message format from client

Message-Level Errors

Error Code Condition Response
400 Invalid message format Error message, connection continues
400 Missing 'type' field Error message, connection continues
400 Unexpected message type Error message, connection continues
4004 Chat initialization failure Connection closed
4006 Internal server error Connection closed
4007 History transmission error Connection closed

Error Message Format

{ "type": "error", "error": "Error description", "status_code": 400 }

Phase 5: Connection Termination

Graceful and Unexpected Disconnections

Normal Termination

  • Client closes WebSocket connection
  • Server logs disconnection with session ID
  • Resources are automatically cleaned up

Error-Based Termination

  • Authentication failures result in immediate closure
  • Critical errors trigger server-initiated closure
  • Network issues cause unexpected disconnections

Cleanup Process

  1. LLM instance resources are released
  2. Chat session state is persisted
  3. Connection termination is logged
  4. Memory cleanup occurs automatically

Performance Considerations

Optimization Features

  • Streaming Responses: Real-time token delivery for better UX
  • History Limiting: Only last 10 messages sent to reduce bandwidth
  • Session-Scoped Tools: Tools configured once per session, not per message
  • Async Processing: Non-blocking message handling with async/await
  • Efficient JSON: Using ujson for faster JSON operations

Security Measures

Security Implementation

  • JWT Authentication: Token-based session validation
  • User Scoping: All tools and data access are user-scoped
  • IP Logging: Client IP addresses tracked for security audit
  • Session IDs: Unique session tracking for monitoring
  • Database Verification: User existence verified on each connection
  • Graceful Error Handling: No sensitive information leaked in errors

Client Implementation Guidelines

Recommended Client Behavior

  1. Connect: Establish WebSocket connection to endpoint
  2. Authenticate: Send JWT token immediately after connection
  3. Wait for Auth Success: Process auth_success before sending messages
  4. Handle History: Process history_messages to restore conversation
  5. Send Messages: Use proper message type structure
  6. Handle Streaming: Process both JSON events and raw text tokens
  7. Error Recovery: Implement reconnection logic for dropped connections
  8. Graceful Closure: Close connection properly when done

Monitoring and Logging

Comprehensive Logging Strategy

Log Levels and Events

  • INFO: Connection events, authentication success/failure
  • DEBUG: Message processing, token streaming, tool execution
  • WARNING: Unknown message roles, unexpected conditions
  • ERROR: Exception handling, processing failures

Tracked Metrics

  • Session duration and message count
  • Tool execution frequency and success rates
  • Error rates by type and session
  • Authentication failure patterns
  • Response streaming performance
